# AI駆動システム開発フェーズ定義書

## 1. 目的

本文書はAntigravity環境の下でシステム開発を行うための開発フェーズと手順を記述するものである。

## 2. 開発フェーズと内容

以下に開発フェーズと開発手順を記述する。

### 2.1. PHASE 1 プロジェクトの準備

本フェーズでは新規開発プロジェクトの準備として、プロジェクト用のディレクトリ作成とAntigravityでのプロジェクト作成を行い、Antigravity上での手順書を読み込む。

1. プロジェクト名を決定し、プロジェクト用のディレクトリを`/Users/sakyo/Documents/workspace/AI/`配下に作成する。
2. Antigravityでプロジェクトを作成し、本手順書と配下のprompts/フォルダをプロジェクト内にコピーする。
3. 手順書/配下のドキュメントをプロジェクト用に修正するようにAIへ指示する。
4. `/prompts/dev_project_setup.txt` を読み込み、プロンプトを入力する。

---

### 2.2. PHASE 2 要件定義

本フェーズでは要件定義書を作成する。

#### 2.2.1. 要件定義書の作成

1. PHASE1で作成された `docs/要件定義書.md`を編集し、要件定義を完成させる。
2. AIに指示し、`docs/`配下のドキュメントを読み込ませて`docs/要件定義書.md`を清書させる。
3. 文書をレビューし、必要ならドキュメント修正を指示する。

---

### 2.3. PHASE 3 基本設計書の作成

要件定義書を元に、以下の基本設計書を作成する。

- `docs/技術要件定義書.md`
- `docs/ビジネスロジック仕様書.md`
- `docs/画面仕様書.md`
- `docs/テーブルスキーマ定義書.md`

#### 2.3.1. 技術要件定義書の作成と基本設計書の整合性チェック

1. `/prompts/dev_design_setup.txt` を読み込み、プロンプトを入力する。
2. artifactsに文書の分析が表示されるので、必要ならドキュメント修正を指示する。
3. 設計書が出揃ったところで、ドキュメント相互に矛盾がないかを以下の手順で確認する。
   1. `/prompts/dev_review_documents.txt` を読み込み、プロンプトを入力する。
   2. artifactsに文書の分析が表示されるので、必要ならドキュメント修正を指示する。
   3. /docs配下のドキュメントに矛盾がなくなるまで1.〜2.を繰り返す。

---

### 2.4. PHASE 4 開発環境とシステム構築

本フェーズではローカルに開発環境を構築し、基本設計書に基づいてシステムの開発を行う。

1. `/prompts/dev_environment_setup.txt` を読み込み、プロンプトを入力する。
2. artifactsに環境構築手順と質問事項が表示されるので、手順を確認する。
3. 環境構築手順に問題がなければ、質問事項に回答し、手順の実行を指示する。
4. 開発環境でシステムが起動することを確認する。

---

### 2.5. PHASE 5 ウォークスルー

本フェーズでは動作確認テストのウォークスルーを行う。

1. PHASE 4 で構築した開発環境でシステムを起動し、動作確認を行う。
2. 問題点や訂正箇所を洗い出し、適時AIに指示を出しながら修正・デバッグを行う。
3. ウォークスルーが完了したら、修正によってドキュメントに矛盾が生じていないかを以下の手順でレビューする。
   1. `/prompts/dev_review_documents.txt` を読み込み、プロンプトを入力する。
   2. artifactsに文書の分析が表示されるので、必要ならドキュメント修正を指示する。
   3. `/docs`配下のドキュメントに矛盾がなくなるまで4.〜5.を繰り返す。

---

### 2.6. PHASE 6 スルーテスト環境の構築と実施

本フェーズでは、自動テストコードが実行できる環境を構築した後、テストケースに基づきスルーテストを実行する。
テスト結果がすべて合格するまでシステムの修正とテストを繰り返す。

1. `/prompts/dev_test_setup.txt` を読み込み、プロンプトを入力する。
2. シナリオテスト計画書をレビューし、テストシナリオを確認する。必要があれば修正を指示する。
3. シナリオテスト計画書に則ってテストを実施するように指示する。
4. テスト結果を確認し、エラーの修正を指示する。
5. エラーが無くなるまで3.〜4.を繰り返す。
6. テストが完了したら、修正によってドキュメントに矛盾が生じていないかを以下の手順でレビューする。
   1. `/prompts/dev_review_documents.txt` を読み込み、プロンプトを入力する。
   2. artifactsに文書の分析が表示されるので、必要ならドキュメント修正を指示する。
   3. `/docs`配下のドキュメントに矛盾がなくなるまで1.〜2.を繰り返す。

---

### 2.7. PHASE 7 本番リリース

本フェーズでは、PHASE 6まで完了したシステムを本番環境にリリースする。

#### 2.7.1. 本番リリース作業

1. `/prompts/dev_release_setup.txt` を読み込み、プロンプトを入力する。
2. artifactsに文書やソースコードの矛盾点が表示された場合は、対処方法を検討し指示する。
3. 文書に問題がなくなれば、手順を続行し、`docs/本番適用作業手順書.md`を完成させる。
4. `docs/本番適用作業手順書.md`のレビューを行う。誤りや問題点を発見した場合は修正を指示する。
5. `docs/本番適用作業手順書.md`に基づき、本番リリースの実行を指示する。

#### 2.7.2. 本番環境の設定変更

1. `cloud console`のメニューから`cloud run functions`→今回リリースしたサービスの詳細画面を開き、`セキュリティ`セクションを確認する。
2. 認証の`IAM`と`IAP`の両方にチェックが入っていることを確認する。入っていなければチェックする。
3. `IAP`の`ポリシーの編集`をクリックし、`IAP のコンテキストアウェア アクセス ポリシー`画面を開く。
4. `Principal`列に自分のメールアドレスを入力し、`保存`ボタンをクリックする。
5. `認証`画面の`AllUsersアクセス権を削除`をクリックし、アクセス権を自分だけに設定する。
6. `保存ボタン`を忘れずクリックする。忘れると、アクセスポリシーの設定が失われるので注意する。

#### 2.7.3. 本番リリース後の最終チェック

1. 本番リリース時にartifactsに表示されたURLにブラウザでアクセスし、正常に画面が表示されることを確認する。
2. 動作確認を行う。不具合があれば修正し、再度リリースを行う。

---

### 2.8. PHASE 8 ドキュメント改訂管理の開始

本フェーズでは、PHASE 7で本番リリースを終えたシステムに対し、今後の改定作業の履歴過程を残すためのルールを策定する。

1. `/prompts/dev_rule_setup.txt` を読み込み、プロンプトを入力する。
2. プロジェクトルート直下にAGENTS.md, GEMINI.md, .agents/rules/system-revision.mdの3つの設定ファイルが作成されていることを確認する。
