# ビジネスロジック仕様書 (BUSINESS_LOGIC_SPECIFICATION)

## 1. 概要

本ドキュメントは、「**bicycle-log**」における主要機能の判定基準、計算アルゴリズム、Strava API同期、滞在自動検知（Stop Detection）、Google Places API二重キャッシュ、画像最適化、およびマスタデータ保護制御などのビジネスロジックを定義する。

---

## 2. Strava API 同期 & 滞在自動検知 (Stop Detection) アルゴリズム

### 2.1 自動同期トリガー
- **発生条件**: ユーザーが同日内に本システムへ最初にログインした際（または手動同期ボタン押下時）。
- **同期範囲**: データベース内 `activities` テーブルの最新 `start_date` を特定し、それ以降に実施された未取得の Strava アクティビティを一括取得・保存する。

### 2.2 滞在自動検知アルゴリズム (Stop Detection)

```mermaid
flowchart TD
    A[Strava Activity Streams 取得] --> B[latlng, time, moving ストリームを配列走査]
    B --> C{時空間クラスタリング<br/>半径 R 30m-50m 以内に<br/>留まっているか？}
    C -- いいえ --> B
    C -- はい --> D{経過時間 (t_B - t_A)<br/>>= 1800秒 (30分) か？}
    D -- いいえ --> B
    D -- はい --> E[滞在地点クラスタの確定]
    E --> F[滞在重心座標 Lat_stop, Lng_stop の算出]
    F --> G[到着日時 Arrived At / 出発日時 Left At / 滞在時間の算出]
    G --> H[Google Places API 二重キャッシュ処理へ]
```

#### 1. 判定パラメータ
- **滞在時間閾値 ($\Delta t$)**: **1800秒 (30分) 以上**
- **滞在判定半径 ($R$)**: **半径 30m ～ 50m 以内**

#### 2. アルゴリズム詳細手順
1. **ストリームデータ走査**:
   - Strava Activity Streams API (`GET /activities/{id}/streams`) から取得した `latlng`（座標）, `time`（経過秒数）, `moving`（移動中フラグ）配列を時系列順に精査する。
2. **静止点クラスタ検出**:
   - 時点 $t_A$ から $t_B$ までの位置座標群が半径 $R$ 内に収まり、かつ $(t_B - t_A) \ge 1800\text{秒}$ である区間を滞在クラスタとして抽出する。
3. **滞在重心座標 (Centroid) の算出**:
   - クラスタに含まれる全位置座標の平均値から代表緯度経度 $(Lat_{stop}, Lng_{stop})$ を算出する。
$$\text{Lat}_{stop} = \frac{1}{N}\sum_{i=1}^{N} \text{Lat}_i, \quad \text{Lng}_{stop} = \frac{1}{N}\sum_{i=1}^{N} \text{Lng}_i$$
4. **日時データの決定**:
   - 到着日時 `arrived_at` = `start_date` + $t_A$ (JST)
   - 出発日時 `left_at` = `start_date` + $t_B$ (JST)
   - 滞在時間 `stay_duration_seconds` = $t_B - t_A$ （秒）

## 3. Google Places API 連携 & 二重キャッシュ制御ロジック

Google Places API の呼び出し回数および課金を最小化するため、ローカル DB による二重キャッシュ制御を行う。

```mermaid
flowchart TD
    A[検出した滞在重心座標 Lat_stop, Lng_stop] --> B{DB places テーブル内<br/>半径 50m 以内に<br/>登録済スポットが存在するか？}
    B -- はい (一次キャッシュヒット) --> C[既存 spot/place_id を適用<br/>(API呼び出しスキップ)]
    B -- いいえ (未登録) --> D[Google Places API<br/>Nearby Search 50m 呼び出し]
    D --> E{スポット情報取得成功か？}
    E -- 成功 --> F[Place ID, 名称, 住所, カテゴリを DB 保存]
    E -- 失敗/該当なし --> G[「未分類の滞在スポット」として仮登録]
    C --> H[stay_logs レコードの作成・紐付け]
    F --> H
    G --> H
```

### 3.1 DB近隣検索（一次キャッシュ）
- 新たに抽出された滞在重心座標 $(Lat_{stop}, Lng_{stop})$ に対し、`places` テーブル内の全スポットとの球面距離（Haversine式等）を計算する。
- **50m 以内** に既存スポットが存在する場合、Google API の呼び出しを完全にスキップし、既存スポットの `id` (`place_id`) を `stay_logs` テーブルに紐付ける。

### 3.2 Google Places API (Nearby Search) の呼び出し
- DB 未登録の場合のみ、`Google Places API (Nearby Search)` を呼び出す。
  - **検索パラメータ**: `location=Lat_stop,Lng_stop`, `radius=50`, `rankby=prominence`
  - **カテゴリ割り当て**: 取得した `types` からカフェ, レストラン, 公園, 道の駅, コンビニ等の優先度の高いカテゴリを決定し、`place_categories` マスタとマッピングする。
- 施設が検出されなかった場合は「未分類の滞在スポット」として作成し、後から画面仕様書 (`SCR-02` / `SCR-03`) に基づきユーザーが名称・カテゴリを手動編集可能とする。

## 4. 画像アップロード & 圧縮制御ロジック

### 4.1 画像最適化・WebP変換処理
1. **アップロード処理**:
   - ユーザーが滞在記録に対して写真をアップロードする際、クライアントサイド（HTML5 Canvas API）またはバックエンド処理で最適化を行う。
2. **変換ルール**:
   - **解像度**: 中央基準クロップ (Center Crop) により **700px × 700px 正方形** にリサイズ。
   - **品質**: **80%** (0.8) に圧縮。
   - **フォーマット**: **WebP 形式 (`image/webp`)** へ自動変換。
3. **ストレージ保存**:
   - 最適化後の WebP 画像を GCS バケットへ送信し、生成された URL を `stay_log_images.image_url` に保存する。

### 4.2 外部 Web 画像 URL ダイレクト参照
- ユーザーが外部 Web 上の画像 URL を直接指定した場合、GCS へのファイル送信・変換を行わず、そのまま `stay_log_images.image_url` に URL 文字列を登録・表示する。

### 4.3 複数画像表示順 (`display_order`) 自動採番
- 1件の滞在記録に対し複数枚の画像を追加登録する際、追加順に `display_order = 1, 2, 3...` を自動採番しギャラリーの表示順として適用する。

## 5. ヒートマップ描画 & 通過アクティビティ重なりロジック

### 5.1 Polyline ヒートマップ描画
- 全アクティビティの Polyline データを Google Maps 上に重ね合わせてヒートマップ描画する。

### 5.2 重複ルートの一本化および通過アクティビティ抽出
- 同一の道路・ルートを複数回走行している場合、地図上にはPolylineを重なって濃く描画せず、1本の統合ラインとして表現する。
- **クリック時のインタラクティブ動作**:
  - ユーザーがヒートマップ上の任意のルートまたは滞在スポットをクリックした際、該当する路線・地点を通過した全アクティビティ (`activities`) のリストをダイアログ表示する。
  - 選択されたアクティビティの Polyline を半透明カラーで地図上に重畳強調表示する。
  - 一覧には Strava のライド詳細ページへの外部ダイレクトリンク (`https://www.strava.com/activities/{id}`) を配置する。

---

## 6. マスタ管理・データ保護制御ルール

### 6.1 参照整合性と削除保護
- **削除制御方針**: 自転車マスタ (`bikes`) や滞在カテゴリマスタ (`place_categories`) などのマスタデータを削除しようとした際、既にそのマスタを参照している `activities` や `places` のレコードが存在する場合、**物理削除を拒否し HTTP 409 Conflict エラーを返却**する。

### 6.2 データバリデーション
- **Bike ID / 識別キー形式**: 一意性をチェックし、必須入力項目および型制約を判定する。

---

## 7. タイムゾーンおよび集計可視化ロジック

- **タイムゾーン統一**: すべての記録日時・API入出力データは **日本標準時 (JST, UTC+9 / Asia/Tokyo)** を適用する。
- **ダッシュボード & 可視化集計**:
  - 自転車 (`bike_id`) ごとの「走行距離 (km)」「総上昇量 (m)」「総時間 (時間)」「ライド回数 (回)」「消費カロリー (kcal)」を、「年間」「月間」「週間」の指定タイムレンジで動的に集計・再描画する。
  - 滞在スポットの訪問回数上位 10 件をランキングとして抽出しダッシュボード (`SCR-01`) に表示する。
