# **技術要件定義書 (TECHNICAL_REQUIREMENTS)**

## **1. システム全体アーキテクチャ**

本システムは、「**bicycle-log**」として、M4 Mac mini 上のローカル Docker 環境で自律開発・検証を行い、本番運用時は Google Cloud の「Cloud Run」へデプロイする二段階のハイブリッドホスティング戦略を採用する。

- **ローカル開発環境 (Docker Compose)**: フロントエンド (`frontend`: React / Vite 3000ポート) とバックエンド (`backend`: FastAPI 8000ポート) を独立したコンテナとして動作させ、高速な HMR (Hot Module Replacement) とデバッグ環境を提供する。
- **E2Eテスト環境（Playwright）**: 本システム全体の統合テストおよびシナリオテストを自動実行するため、`tests/e2e/` に Playwright テスト環境を整備する。
- **本番運用環境 (Cloud Run + Litestream + IAP)**:
  - フロントエンド (React ビルド成果物) とバックエンド (FastAPI) を同一の Dockerfile（マルチステージビルド）で単一コンテナイメージへパッケージ化し、Cloud Run 上で単一統合サービスとして稼働させる。
  - **ログイン認証とアクセス制限**: 本システムは Cloud Run の Identity-Aware Proxy (IAP) により、ユーザーのログイン認証およびアクセス制御を行う。
  - **データベース構成 (SQLite + Litestream)**: 低コストかつ高信頼な **SQLite + Litestream** 方式を採用し、バックグラウンドで SQLite の変更ログ（WAL）を GCS (Google Cloud Storage) バケットへリアルタイムレプリケーション・自動復元する。
  - **Litestream 運用の留意事項**:
    - **インスタンス制限**: 複数コンテナによる Litestream の書き込み衝突および WAL データ不整合を防ぐため、Cloud Run の最大インスタンス数を `max-instances=1` に制限設定する。
    - **バックアップ用バケット名のユニーク化**: 同一 GCP プロジェクト上で複数のサービスを稼働させるため、バックアップ用 GCS バケット名には Docker コンテナ名を含めてユニーク化を図る（例: `<project-id>-litestream-bicycle-log`）。

## **2. 各レイヤの採用技術（技術スタック）**

### **2.1. タイムゾーン運用方針 (System Timezone Policy)**

- **標準タイムゾーン**: システム内で保持、出力、表示されるすべての記録日時、ログタイムスタンプ、API レスポンスの日付文字列は **日本標準時 (JST, UTC+9 / Asia/Tokyo)** を適用する。
- **コンテナ環境**: コンテナ起動時の環境変数 `TZ=Asia/Tokyo` を統一適用する。

### **2.2. データベースレイヤ (Database Layer)**

- **採用技術**: SQLite 3 (単一ファイル型組み込み RDB) + Litestream (GCS レプリケーション)
- **データ保存・永続化方針**: コンテナ内部の `/app/data/app.db` で管理し、本番環境では Litestream サービスが起動時に GCS バケットから最新の `app.db` をリストアし、稼働中はリアルタイムで WAL 変更ログを GCS へ非同期書き込みすることで、データ損失ゼロと高速アクセスを両立する。
- **Litestream 運用要件**:
  - **Cloud Run 最大インスタンス制限**: 複数コンテナ（マルチインスタンス）による同データファイルへの同時競合書き込みを防ぐため、Cloud Run のスケール設定で最大インスタンス数を `max-instances=1` に固定制限する。
  - **バックアップバケットのユニーク化**: 他サービスとのバケット衝突を避けるため、バックアップ用 GCS バケット名には Docker コンテナ名を入れて命名する（例: `<project-id>-litestream-bicycle-log`）。

### **2.3. バックエンド・サーバーレイヤ (Backend Layer)**

- **採用言語**: Python 3.11+
- **採用フレームワーク**: FastAPI (SQLAlchemy / SQLModel ORM)
- **採用周辺技術**:
  - `pydantic-settings` (Pydantic ベースの環境変数バリデーション・ロード、`APP_VERSION` 等)
  - `google-cloud-storage` (Google Cloud Storage SDK 連携・画像オブジェクトアップロード/参照)
  - `httpx` / `requests` (Strava API / Google Places API 非同期・同期通信)
  - `AI駆動構造化JSONロギング (logging, sys.stdout)`: JST, UUIDv4 `log_id` 自動バインド, 動的ログレベル変更 API (`POST /api/internal/logger/level`, 認証キー: `INTERNAL_AI_TOKEN`)。
- **主要バックエンド API エンドポイント**:
  - Strava自動同期・データ取得API (`POST /api/strava/sync`)
  - 走行ログ発着点検出・一括遡及API (`POST /api/strava/backfill-endpoints`)
  - 滞在スポット・定番ルート横断検索API (`GET /api/search`)
  - システムバージョン取得API (`GET /api/system/version`)
  - 滞在検出・Google Places検索API
  - 各エンティティ (`bikes`, `place_categories`, `places`, `activities`, `stay_logs`, `routes`, `tags`) の CRUD 操作 API
  - ヒートマップ/統計データAPI (`GET /api/analytics/heatmap`, `GET /api/analytics/summary`)
  - 画像アップロード連携 API (`POST /api/stay-logs/{id}/images`)

### **2.4. フロントエンド・プレゼンテーションレイヤ (Frontend Layer)**

- **採用技術**: React (Vite ビルド環境) + Tailwind CSS + `Lucide React` + Google Maps API (JavaScript API)
- **構成要素**:
  - SPA（シングルページアプリケーション）構造。
  - **トップバー・バージョン表記**: `GET /api/system/version` と連動し、ヘッダーロゴ横にカレントバージョン（`v1.2`）を常時表示。
  - **リアルタイムサジェスト検索**: ダッシュボードトップバナーにて滞在スポットおよび定番ルートをリアルタイム絞り込み・直接遷移。
  - **ヒートマップ機能拡張**: 全画面フルスクリーン拡大トグル表示、およびルートクリック時の地図上サブウィンドウ（オーバーレイ情報カード）表示。
  - **表示モード切替（マルチテーマ）**: `light` / `dark` / `system` (OS設定追従) の切り替え状態管理および DOM への `dark` クラス動的連動。
  - GCP Cloud Run IAP ヘッダー (`x-goog-authenticated-user-email` / `x-goog-iap-jwt-assertion`) によるシームレスな自動ログイン・アクセス制限・ユーザー識別。

## **3. 外部サービス連携・画像ストレージ連携仕様**

### **3.1 Strava API 連携仕様**
- **認証方式**: OAuth 2.0 (Access Token / Refresh Token 管理)
- **連携エンドポイント**:
  - `GET /athlete/activities`: 同日初回ログイン時、前回取得日時以降の新規アクティビティ一覧を取得。
  - `GET /activities/{id}/streams`: 滞在検知用に `latlng`（位置座標）、`time`（経過時間秒）、`moving`（移動フラグ）の時系列ストリームデータを取得。
- **走行ログ開始点・終了点抽出仕様**:
  - 各アクティビティの `summary_polyline` をデコードし、最初と最後の座標から発着点を抽出。
  - Google Places API およびローカルDBキャッシュ（50m）と連動してスポットを特定・生成し、滞在時間0秒の StayLog 2件（スタート・ゴール）を登録。

### **3.2 Google Places API 連携 & キャッシュ仕様**
- **連携エンドポイント**: `Nearby Search API` (`location=lat,lng`, `radius=50`, `rankby=prominence`)
- **キャッシュ制御**: 滞在検知時にまずローカル DB (`places`) の半径 50m 以内を検索（一次キャッシュ）。ヒットした場合は API 呼び出しを行わず既存 `place_id` を紐付け。未登録の場合のみ API を呼び出して `places` テーブルへ新規保存。

### **3.3 Google Cloud Storage (GCS) 画像保存・最適化仕様**

- **保存・参照方針**:
  - 写真・添付画像は GCS バケット内に保存し、参照 URL を DB (`stay_log_images.image_url` 等) に記録する。
  - 外部 Web 上の画像 URL をダイレクト指定する場合は GCS への保存を行わず参照 URL のみ保存・利用する。
- **フロントエンド / バックエンド画像最適化要件**:
  - **リサイズ・クロップ**: **700px × 700px 正方形 (Center Crop)**
  - **圧縮フォーマット**: **WebP 形式 (Quality: 80%)**
  - **ストレージ保存**: クライアントサイド (Canvas API) または バックエンド経由で最適化済みの軽量 WebP ファイルを作成し GCS へ送信・保存。

## **4. セキュリティおよび認証方針**

- **認証方式 (GCP Cloud Run IAP 認証)**:
  - ログイン認証およびアクセス制御には **GCP Cloud Run IAP (Identity-Aware Proxy)** を採用する。
  - Cloud Run 前段で Google ログイン認証が行われ、アプリへは注入された `x-goog-authenticated-user-email` / `x-goog-iap-jwt-assertion` ヘッダー経由でユーザー識別情報を取得・検証・連携する。ローカル開発環境では開発用ダミー認証ヘッダーへ自動フォールバックを行う。
- **API キー・シークレット安全管理方針**:
  - フロントエンドコード内に Strava API Secret, Google Places API Key, GCP クレデンシャル等を一切含めず、すべて FastAPI バックエンドがプロキシ通信する。
  - ソースコードリポジトリ (Git) から `.env` や認証鍵 JSON、`app.db` を完全除外する。
- **環境変数注入**:
  - **開発環境 (ローカルDocker)**: `docker-compose.yml` で `backend/.env` から環境変数をコンテナ内へ注入する。
  - **本番環境 (Google Cloud / Cloud Run)**: GCP `Secret Manager` 上にシークレットを安全に登録し、Cloud Run のサービス起動時に動的に環境変数として注入する。

## **5. AI駆動開発（Antigravity 2.0）コントロール要件**

- **開発プロセス**: 成果物はチャット上の Artifacts にコード出力し、人間の承認を得てから適用する。
- **自律実行の制約**: 1タスクにつき自律デバッグ試行回数は最大5回までとし、ファイル変更確定前に必ず Diff を提示する。
- **自律デバッグ & ログ照会プロトコル**:
  - HTTP 500エラー発生時、レスポンスに含まれる一意の `log_id` (UUIDv4) をキーにして標準出力の構造化JSONログを検索。
  - 動的ログ変更エンドポイント (`POST /api/internal/logger/level`) を活用し、コンテナを再起動することなく DEBUG モードへ切り替えて調査を行う。
