# 要件定義書 (bicycle-log)

## 1. システムの概要

### 1.1 システムの呼称
本システムは **bicycle-log** と呼称します。

### 1.2 目的
本システムは、自転車（サイクリング/ポタリング）のアクティビティデータおよび立ち寄り地点（カフェ、道の駅、公園等）の滞在記録を自動的に抽出・管理・可視化し、個人の走行履歴や訪問スポットを一覧および地図上で一元管理することを目的とします。

### 1.3 対象ユーザーおよび運用形態
本システムは個人（または特定の管理者）による利用を前提としたウェブアプリケーションであり、Google Cloud (Cloud Run) 上で運用されます。

---

## 2. システム機能要件

### 2.1 ダッシュボード機能
- **主要サマリー表示**: 総走行距離、総上昇量、総ライド回数、累積滞在スポット数等のシステム主要データを可視化します。
- **インジケーター / グラフィック**: 視覚的なインジケーターや最新のアクティビティ状況を直感的に把握できるグラフィックを表示します。
- **直近アクティビティ表示**: 直近に実施されたアクティビティの概要を表示します。
- **滞在記録ランキング**: 滞在記録の訪問回数上位ランキング（表示件数: 上位10件）を表示します。
- **発着点一括検出アクション**: 過去のアクティビティ全件（または指定期間）に対して、開始点およびゴール地点の滞在スポット・ログを一括検出・生成する手動トリガーを提供します。

### 2.2 検索機能
- **リアルタイム絞り込み検索**: 管理対象のアクティビティ、滞在スポット、および各種マスタデータを、キーワード（名称、概要、住所、カテゴリ、備考等）によってリアルタイムに絞り込み・検索できる機能を提供します。
- **ダッシュボード横断検索（リアルタイムサジェスト）**: ダッシュボードのトップバナー内に検索窓を設置し、滞在スポット（Place）および定番ルート（Route）をキーワード入力時にリアルタイムで横断検索し、カテゴリやアイコン付きのサジェストリストから目的の詳細画面へ直接遷移できる機能を提供します。

### 2.3 マスタ管理機能
- **画面からの CRUD 操作**: 各種マスタデータを画面から登録（Create）、参照（Read）、編集（Update）、削除（Delete）可能とします。
- **対象マスタデータ**:
  - 自転車マスタ (`bikes`): 所有する自転車の識別情報（Bike ID、名称、ブランド、モデル、登録日等）
  - 滞在カテゴリマスタ (`place_categories`): カフェ、レストラン、公園、道の駅、コンビニ等の自動判別およびアイコン表示用カテゴリ定義
  - 定番ルートマスタ (`routes`): 走行軌跡の類似度が一定値（70%超）以上の類似アクティビティをグルーピングした定番コース定義
  - タグマスタ: アクティビティやスポットに付与するカスタムタグ情報

### 2.4 一覧画面機能
- **データ一覧表示**: 各種データ（アクティビティ一覧、滞在スポット一覧等）の一覧画面を提供します。
- **ページネーション & ソート**: ページネーション表示、および多角的なカラムによる昇順・降順ソート機能を提供します。
- **詳細・編集モーダル連携**: 一覧から各レコードを選択した際、詳細表示および編集を行うモーダルダイアログとスムーズに連携します。

### 2.5 Strava連携 & 滞在自動検知機能
- **自動同期トリガー**: 本システムに同日内に最初にログインした際、システム内のアクティビティデータの最新日付を確認し、その日付以降のStravaアクティビティデータを自動取得して保存します。
- **時系列 Streams API データの活用**:
  - `Strava Activity Streams API` (`GET /activities/{id}/streams`) を利用し、`latlng`（位置座標）、`time`（経過秒数）、`moving`（移動フラグ）の時系列データを取得します。
- **滞在検知アルゴリズム (Stop Detection)**:
  - **滞在判定条件**: 時空間クラスタリングを用い、位置座標群が半径 30m〜50m 以内に留まり、かつ経過時間が **30分 (1800秒) 以上** 移動停止している区間を滞在地点として自動検出します。
  - **滞在情報の算出**: 滞在区間内の GPS 重心座標 $(Lat_{stop}, Lng_{stop})$、到着日時 (`arrived_at`)、出発日時 (`left_at`)、滞在時間（秒）を確定して記録します。
- **走行ログ開始点・終了点の滞在スポット化（発着点検出）**:
  - アクティビティの `summary_polyline` から開始点座標および終了点座標を抽出します。
  - Google Places API / 二重キャッシュ構造と連携してスポット（Place）を特定・生成します。
  - 各アクティビティに対して「スタート地点」および「ゴール地点」の滞在ログ（StayLog、滞在時間0秒）をそれぞれ1件ずつ計2件記録します（周回コースで同一スポットの場合も時系列で2件登録）。
  - 通常のStrava同期時における自動生成に加え、既存全アクティビティへの一括遡及登録API (`POST /api/strava/backfill-endpoints`) を提供します。
- **Google Places API 連携 & 二重キャッシュ構造**:
  - 検出した滞在重心座標に対し、まず自システム DB 内の `places` テーブルから半径 50m 以内の登録済みスポットを検索（一次キャッシュ）。
  - 既存スポットが存在すれば Google API の呼び出しをスキップし、既存の `place_id` を適用。
  - DB 未登録の場合のみ `Google Places API (Nearby Search)` を呼び出し、スポット名称、住所、カテゴリ情報を取得して保存。APIで特定できない場合は「未分類の滞在スポット」として仮登録し、手動修正を可能とします。

### 2.6 データ移行プログラム (初回・テスト移行)
- **専用移行プログラム**: 本番リリース時に全期間のアクティビティデータ、滞在記録、および Place データを一括で過去遡及取得・抽出・保存する専用データ移行プログラムを導入します。
- **テスト用パラメータ対応**: 本プログラムはパラメータ指定（例: 直近 $n$ ヶ月）により、指定した過去期間のみを対象として段階的にデータを取り込むテスト実行機能を備えます。

### 2.7 滞在記録 & マップ機能
- **Google Maps 表示 & マーカー描画**: Google Maps を表示し、滞在記録を地図上にマーカーでプロット表示します。
- **カテゴリ自動判別アイコン**: 滞在記録のカテゴリに応じた専用のマーカーアイコンを設定・表示します。
- **スケールグルーピング (Cluster)**: 地図の一定縮尺以下で近接するマーカーアイコンを自動的にグルーピング表示し、グループアイコン内に含まれる滞在記録件数を表示します。
- **コメント・写真添付機能**:
  - 各滞在記録に対してユーザーによる任意コメントおよび複数写真の添付を可能とします。
  - **写真保存・圧縮要件**: アップロードされた写真はバックエンドで自動的に WebP フォーマット・品質 80% 圧縮に変換した上で Google Cloud Storage (GCS) へ保存します。
  - **Web参照 URL 指定**: 外部 Web 上の画像 URL をダイレクト指定して紐付けることも可能とし、この場合はストレージへのアップロードを行わず参照 URL のみ保持します。
- **Google Maps Place 詳細リンク**: 該当地点の Google Maps Place 情報（URL）を表示し、クリック時に Google Maps の詳細ページへ遷移可能とします。
- **通過アクティビティ一覧遷移**: 滞在記録の詳細画面から、該当スポットを通過したアクティビティ一覧画面へシームレスに遷移する機能を提供します。

### 2.8 データのグラフ化・可視化機能
- **多角的グラフ可視化**: Stravaのアクティビティデータから、Bike ID ごとに以下のメトリクスを可視化します。
  - 走行距離 (km)
  - 総上昇量 (m)
  - 総時間 (時間)
  - ライド回数 (回)
  - 消費カロリー (kcal)
- **タイムレンジ切り替え**:
  - 「年間」「月間」「週間」の切り替えボタンを提供し、ボタン押下時にそれぞれの集計期間レンジでグラフを動的に再描画します。

### 2.9 ヒートマップ表示機能
- **Polyline ヒートマップ描画**: Stravaアクティビティデータの Polyline 情報をもとに、Google Maps 上に走行軌跡のヒートマップを表示します。
- **インタラクティブ表示 & 重ね合わせ**:
  - ヒートマップ上の任意の路線/位置をクリックした際、その場所を通ったアクティビティの Polyline を半透明で地図上に重ねて表示します（元のヒートマップは背景に保持）。
- **定番ルート優先統合描画**:
  - 定番ルートマスタ (`routes`) に紐づけられたアクティビティ群は個別の線描画を行わず、代表 Polyline を 1 本に統合して描画します。クリック時には配下の全アクティビティをリスト提示します。
- **ヒートマップ全画面拡大表示機能**:
  - ヒートマップ右上に全画面拡大トグルボタンを設置し、クリック時に画面全体へマップを展開して広範囲な走行軌跡の閲覧を可能とします。
- **ルート選択時の地図上サブウィンドウ表示**:
  - 地図上でルート（定番ルートまたは単体アクティビティ）をクリックした際、地図内にオーバーレイサブウィンドウ（情報カード）を表示し、ルート名、走行回数/距離、および詳細画面・マスタ画面への直接導線を提供します。
- **Strava ライド詳細ページ遷移**:
  - 表示されたアクティビティ一覧には Strava のライド詳細ページへの直接リンクを掲載し、クリックで Strava の該当ページを開くことができます。

### 2.10 定番ルート自動検知・管理機能
- **類似度判定 & グルーピング**: GPS Encoded Polyline (`summary_polyline`) の幾何学的類似度（球面距離 Haversine 点列照合）が 70% を超えるアクティビティ同士を自動抽出し、定番ルート (`routes`) として一括登録・紐付けます。
- **Strava同期時の自動登録**: Strava同期実行時、新規アクティビティの Polyline が既存定番ルートと 70% 以上の近似性を持つ場合、自動的に定番ルートへ紐付けます。
- **マスタ一覧 & 代表Polyline管理**: マスタ画面にて定番ルート一覧の参照、ルート名の編集、代表 Polyline のマッププレビュー、配下アクティビティ数の確認を行う機能を提供します。

## 3. 非機能要件

### 3.1 認証・アクセス制御
- **Identity-Aware Proxy (IAP) 統合**: 本システムは Google Cloud Run の Identity-Aware Proxy (IAP) を前段に配置し、Google アカウントによる厳格なユーザーログイン認証およびアクセス制御を行います。

### 3.2 データベース & バックアップ要件
- **SQLite 運用 & Litestream レプリケーション**: 本番環境のデータベースには SQLite3 を使用し、サイドカー/プロセス連動型の Litestream により Google Cloud Storage (GCS) へ WAL ログを秒単位でリアルタイムバックアップします。
- **コンテナ最大数制御**: SQLite への複数コンテナからの書き込み競合およびデータベース破損を防ぐため、Cloud Run の最大インスタンス数を `max-instances=1` に制限設定します。
- **バケット命名のユニーク化**: 同一 GCP プロジェクト内での衝突を防ぐため、Litestream バックアップ用 GCS バケット名には Docker コンテナ名を含めてユニーク化を図ります（例: `<project-id>-litestream-<container-name>`）。

### 3.3 可視性・AIファースト自律ロギング要件
- **標準出力 (stdout) の完全集約**: Twelve-Factor App の原則に準拠し、すべてのログを標準出力に流し、Docker logs / Cloud Logging による自動回収を行います。
- **構造化 JSON フォーマット**: ログ出力は1行完結の JSON オブジェクトに統一し、タイムスタンプは JST (UTC+9) で統一します。
- **例外ハンドラでの `log_id` 付与**: システムエラー発生時には UUIDv4 による一意の `log_id` を発行してログおよびフロントエンドエラーレスポンス双方に付与し、不具合調査のトレーサビリティを担保します。
- **AI用 動的ログレベル変更 API**: バックエンドのロガーレベルをメモリ上で動的に変更可能なエンドポイント (`POST /api/internal/logger/level`) を設置し、AIエージェント等の自律デバッグを支援します（専用ヘッダー認証付き）。

### 3.4 セキュリティ & APIキー一元管理要件
- **フロントエンド秘匿化の徹底**: クライアント（ブラウザ）側には GCP サービスアカウントキーや秘密情報を一切保持・返却せず、すべての外部サービス通信はバックエンド（FastAPI）が安全にプロキシ通信します。
- **シークレット一元管理**: ローカル環境では `.env` からの環境変数注入、本番環境では GCP Secret Manager を介して Cloud Run コンテナへ安全に注入します。

## 4. 外部インターフェース要件

### 4.1 Strava API
- **認証**: OAuth 2.0 (Access Token / Refresh Token)
- **使用エンドポイント**:
  - `GET /athlete/activities` (アクティビティ一覧取得)
  - `GET /activities/{id}/streams` (時系列位置・時間ストリームデータ取得)

### 4.2 Google Places API
- **使用サービス**: Nearby Search API
- **目的**: 滞在判定座標からのスポット名称・カテゴリ・住所自動取得 (50m 検索)

### 4.3 Google Cloud Storage (GCS)
- **用途 1**: 添付写真の保存 (WebP 80% 圧縮変換後の画像ファイル)
- **用途 2**: Litestream による SQLite バックアップ WAL ストレージ

### 4.4 Google Cloud Run & Identity-Aware Proxy (IAP)
- **ホスティング環境**: Cloud Run 単一統合コンテナ (`max-instances=1`)
- **認証レイヤー**: IAP (コンテキストアウェアアクセスポリシー)

## 5. 共通 UI/UX ・レスポンシブ・インタラクション仕様

### 5.1 デバイス別ブレークポイント (Tailwind CSS)
- **モバイル表示**: 画面幅 767px 以下（Tailwind CSS `md:` 未満）。縦スクロール最適化 layout。
- **デスクトップ表示**: 画面幅 768px 以上。メインコンテナの最大幅を 1800px に拡大（`max-w-[1800px]`）。

### 5.2 ナビゲーション & ハンバーガーメニュー
- **システムバージョン表記**: トップバーのロゴタイトルの右隣に、システムの現在バージョン（例: `v1.2`）をバッジ形式で常時表示します。環境変数 `APP_VERSION` とバックエンド API を介して連動します。
- **ハンバーガーメニュー**: トップバー画面右端にハンバーガーメニューを配置し、マスタメンテナンスや各種ビューへのアクセスリンクを収納します。

### 5.3 マルチテーマ切り替え機能
- 「ライトモード」「ダークモード」「システム (OS設定追従)」の3モード切替をサポートします。
- ナビゲーションバーおよびハンバーガーメニュー内に切替ボタンを配置し、OSの `prefers-color-scheme: dark` 変更にリアルタイム連動します。

### 5.4 ボタン表現ルール
- ボタン機能説明（tooltip / title 属性）はすべて英語表記で統一します。
- 普遍的な操作ボタン（Edit, Delete, Search 等）はミニマルアイコン表示とします。

## 6. 制約事項・運用ルール

1. **書き込みインスタンス数の制限**: Cloud Run の最大インスタンス数は SQLite の排他制御上の理由から常に `1` で運用する必要があります。
2. **添付画像変換処理**: 添付された画像ファイルはサーバーサイドで自動的に WebP (80% 品質) に圧縮変換されるため、元の高解像度生ファイルは直接保持されません。
3. **データ移行プログラムの実行**: 本番導入時およびテスト運用時、過去データの取り込みは環境変数・引数で指定された月数レンジまたは全期間でデータ移行プログラムを呼び出す必要があります。
