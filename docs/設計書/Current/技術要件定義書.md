# 技術要件定義書 (TECHNICAL_REQUIREMENTS)

## 1. システム全体アーキテクチャ (Profile A: クラウド公開型)

本システムは、「**bicycle-log**」として、ローカル Docker 環境で自律開発・検証を行い、本番運用時は Google Cloud の「Cloud Run」へデプロイする二段階のハイブリッドホスティング戦略を採用する。
system-dev-pipeline V2.6 の **Profile A (サーバーレス極小コストWeb型)** に完全準拠する。

- **ローカル開発環境 (Docker Compose)**:
  - フロントエンド (`frontend`: React / Vite 3000ポート) とバックエンド (`backend`: FastAPI 8000ポート) を独立したコンテナとして動作させ、高速な HMR (Hot Module Replacement) とデバッグ環境を提供する。
- **本番運用環境 (Cloud Run + Litestream + IAP + SQLite WAL + Alembic)**:
  - フロントエンド (React ビルド成果物) とバックエンド (FastAPI) を同一の Dockerfile（マルチステージビルド）で単一コンテナイメージへパッケージ化し、Cloud Run 上で単一統合サービスとして稼働させる。
  - **ログイン認証とアクセス制限**: 本システムは Cloud Run の Identity-Aware Proxy (IAP) により、ユーザーのログイン認証およびアクセス制御を行う。バックエンド `core/auth.py` にて IAP JWT 署名二重検証ミドルウェアを配備する。
  - **データベース構成 (SQLite + Litestream + Alembic)**: 低コストかつ高信頼な **SQLite + Litestream** 方式を採用し、バックグラウンドで SQLite の変更ログ（WAL）を GCS (Google Cloud Storage) バケットへリアルタイムレプリケーション・自動復元する。スキーマ変更は Alembic により決定論的に管理する。
  - **Litestream 運用の留意事項**:
    - **インスタンス制限**: 複数コンテナによる Litestream の書き込み衝突および WAL データ不整合を防ぐため、Cloud Run の最大インスタンス数を `max-instances=1` に制限設定する。
    - **バックアップ用バケット名のユニーク化**: 同一 GCP プロジェクト上で複数のサービスを稼働させるため、バックアップ用 GCS バケット名には Docker コンテナ名を含めてユニーク化を図る（例: `<project-id>-litestream-bicycle-log`）。

## 2. 定常コア非機能要件バインド (Universal Core Specifications)

本システムは以下の定常コア非機能要件をアーキテクチャレベルで強制する。

- **[REQ-NF01] Anti-God Component / 行数制限 (Hard Gate)**:
  - フロントエンド: 1ファイル最大 250 行制限。Hooks、UIコンポーネント、Services を物理分離する。
  - バックエンド: 1ファイル最大 400 行制限。SQLAlchemyモデル、ルーター、サービスクラスを適切に分割する。
  - Git pre-commit フックおよび CI で `scripts/harness_guard.py` を実行し、制限超過をコミット前に物理遮断する。
- **[REQ-NF02] 要件トレーサビリティ (RTM 100% カバレッジ & 異常系 20% 以上)**:
  - `scripts/traceability_checker.py` により、要件定義から設計・テストコードまでの 100% 紐付けを機械検証する。
  - 自動テストにおける異常系・境界値テスト比率 20% 以上を保証する。
- **[REQ-NF03] ブラウザ感覚センサー (WCAG AA & エラーゼロ)**:
  - Chrome DevTools MCP による感覚センサー検証（Console Error 0件、WCAG AA 4.5:1 コントラスト比、A11y ツリー適合）を実施する。
- **[REQ-NF04] 型定義自動同期 (OpenAPI ➔ TypeScript Codegen)**:
  - FastAPI の Pydantic スキーマから OpenAPI スキーマを生成し、フロントエンド TypeScript 型定義を完全自動同期する。手動二重定義を排除する。
- **[REQ-NF05] シークレット厳格検証 (Pydantic Settings 起動時即死ガード)**:
  - `pydantic-settings` を用いた起動時バリデーションを実装し、必須環境変数（`DATABASE_URL`, `STRAVA_CLIENT_ID`, `STRAVA_CLIENT_SECRET`, `GOOGLE_MAPS_API_KEY` 等）の欠落時に即座にプロセスを終了させる。
  - クライアントへの秘密情報露出を完全に防止する。
- **[REQ-NF06] 統一タイムゾーン (Aware UTC 保存 / JST 表示)**:
  - データベース保存: すべてのタイムスタンプは Aware UTC (UTC+0) で保存する。
  - API レスポンスおよび画面表示: 日本標準時 (JST, UTC+9 / Asia/Tokyo) へ変換して表示する。
- **[REQ-NF07] モック制御アダプター層 (MSW 集約 & 実結合フォールバック禁止)**:
  - MSW (Mock Service Worker) によるモックハンドラーの一元管理。
  - `VITE_ENABLE_MOCK=true/false` による完全透過切り替え。
  - 実結合モード時のサイレントモックフォールバックを厳格禁止する。
- **[REQ-NF08] 画面グランドデザイン (4px/8px グリッド & 明暗ペア & デイライト視認性)**:
  - 余白・サイズは 4px/8px グリッドに統一。
  - すべての要素にライト・ダークモードの明暗ペア（`dark:`）を指定。
  - 屋外日光下でのデイライト視認性を確保する高コントラスト設計。

## 3. 各レイヤの採用技術（技術スタック）

### 3.1 データベースレイヤ (Database Layer)
- **採用技術**: SQLite 3 (WALモード) + Litestream + Alembic
- **データ保存方針**: `/app/data/app.db` で管理。WAL 変更ログを GCS へ非同期リアルタイムレプリケーション。
- **マイグレーション方針**: 生SQL DDL を禁止し、Alembic マイグレーションスクリプトでバージョン管理を行う。
- **対応要件**: `[REQ-F01]`, `[REQ-F02]`, `[REQ-F03]`, `[REQ-F04]`, `[REQ-F05]`, `[REQ-F07]`, `[REQ-NF06]`

### 3.2 バックエンド・サーバーレイヤ (Backend Layer)
- **採用言語**: Python 3.11+
- **採用フレームワーク**: FastAPI (SQLAlchemy ORM + Pydantic v2)
- **アーキテクチャ方針**:
  - DTO 分離（`schemas/`）によるリクエスト/レスポンス型の明確化。
  - レイヤーバイパスの禁止（ルーターから直接モデルを返却せず、DTO 経由で返却）。
  - レイヤー構造: `routers/` ➔ `services/` ➔ `repositories/` / `models/`
- **主要モジュール**:
  - `core/auth.py`: IAP JWT 二重署名検証ミドルウェア (`[REQ-NF05]`)
  - `core/config.py`: Pydantic Settings 環境変数管理 (`[REQ-NF05]`)
  - `services/strava_service.py`: Strava API 通信・ストリーム解析 (`[REQ-F02]`)（400行制限によりクラスタリング・ストリーム処理を分離）
  - `services/clustering_service.py`: 滞在検知アルゴリズム (`[REQ-F03]`)
  - `services/places_service.py`: Google Places API 二重キャッシュ連携 (`[REQ-F03]`)
  - `services/image_service.py`: WebP 画像リサイズ・GCS アップロード (`[REQ-F04]`)
  - `services/route_matching_service.py`: 定番ルート Haversine 照合 (`[REQ-F05]`)
  - `services/analytics_service.py`: 統計集計・ヒートマップデータ生成 (`[REQ-F06]`)

### 3.3 フロントエンド・プレゼンテーションレイヤ (Frontend Layer)
- **採用技術**: React (Vite ビルド環境) + TypeScript + Tailwind CSS + Lucide React + Google Maps JavaScript API
- **アーキテクチャ方針**:
  - Anti-God Component（1コンポーネント最大250行制限）(`[REQ-NF01]`)
  - 直書きモック排除・MSW 集約 (`[REQ-NF07]`)
  - Hooks / Services / Components の物理分離
- **対応要件**: `[REQ-F01]`, `[REQ-F05]`, `[REQ-F06]`, `[REQ-NF01]`, `[REQ-NF03]`, `[REQ-NF07]`, `[REQ-NF08]`

## 4. 外部サービス連携・キャッシュ戦略

### 4.1 Strava API 連携仕様 (`[REQ-F02]`)
- **OAuth 2.0 認証**: Access Token / Refresh Token による安全なトークン更新。
- **連携エンドポイント**:
  - `GET /athlete/activities`: 新規アクティビティ取得。
  - `GET /activities/{id}/streams`: 滞在検知用時系列ストリーム取得 (`latlng`, `time`, `moving`)。

### 4.2 Google Places API 連携 & 二重キャッシュ戦略 (`[REQ-F03]`)
- **外部API二重キャッシュ戦略**:
  - **第1キャッシュ (TTL インメモリキャッシュ)**: 同一プロセス内での短時間重複リクエストを LRU キャッシュで遮断 (TTL: 10分)。
  - **第2キャッシュ (SQLite DB キャッシュ)**: 過去に特定されたスポット (`places` テーブル) を半径 50m 以内で空間検索。
  - **API 呼び出し**: DB に該当スポットが存在しない場合のみ `Nearby Search API` を呼び出し、結果を DB に永続保存。API コストを極小化する。

### 4.3 Google Cloud Storage (GCS) 連携 (`[REQ-F04]`)
- 滞在ログ写真（WebP 80% 圧縮）のオブジェクト保存および署名付き URL または公開 URL の提供。
- Litestream による SQLite WAL レプリケーション先バケット。
