# システム統合・シナリオテスト計画書 (docs/plans/シナリオテスト計画書.md)

## 1. 概要と目的

本ドキュメントは、「bicycle-log（自転車ログ＆滞在自動検知システム）」における各機能の自律実装・単体テストの完了を受け、システム全体の画面操作および主要API/バックエンド処理を自動化して網羅的な統合シナリオテストを実施する **システム統合・シナリオテストフェーズ** の進め方、必要なテスト環境、およびテストシナリオ案を定義するものである。

本フェーズの主たる目的は以下の通りである：

1. **画面操作・API統合処理の自動化による網羅検証**: ユーザーの操作フローおよびStravaデータ取り込み・滞在自動抽出アルゴリズムに沿ったシナリオテストを自動化し、フロントエンドUI、バックエンドAPI、データベース(SQLite)、GCS画像連携が統合状態で正しく動作することを保証する。
2. **品質評価とレポート化**: テスト実行結果、合格率、失敗箇所のログ・エビデンスを自動出力し、開発チームおよびユーザーへ可視化する。
3. **AI自律デバッグ・スクリプト自動修復 & ユーザー承認サイクルの確立**:
   - テスト失敗が発生した際、AI（Antigravity）がエラー原因を「**テストスクリプトの不具合**」と「**システムの不具合**」の2つに自律分類する。
   - **テストスクリプトの不具合**の場合、AIが自律的にテストコードを修復し、**DB自動復元を経て最大5回までリトライ**を行う（ユーザー承認不要）。
   - **システムの不具合**の場合、原因と修正Diff案を提示して**人間の承認を獲得してからシステムコードを修正**する。

## 2. シナリオテスト全体プロセスフロー

シナリオテストフェーズは、テストシナリオの作成から**DB復元・データ初期化**、自動テスト実行、不具合の原因追跡・自動修復、ユーザー承認に基づくシステム修正、そして再テスト（回帰テスト）までを1つのイテレーティブ（反復型）なサイクルとして運用する。

```mermaid
flowchart TD
    Start([シナリオテストフェーズ開始]) --> Step1[1. シナリオ作成・自動化<br/>統合テスト/E2Eコード構築]

    subgraph IterativeCycle [自動テスト・デバッグ・修復サイクル]
        Step2A[2-A. DB全ドロップ & 復元<br/>data/ から初期化] --> Step2B[2-B. 自動テスト実行<br/>バックエンドAPI & E2Eテスト]
        Step2B --> Judge{全テストパス？}

        Judge -- はい --> StepReport[最終テスト結果レポート作成<br/>docs/reports/V1.0シナリオテスト結果レポート.md]

        Judge -- いいえ (Fail/Abend) --> Step3[3. 原因分類・追跡<br/>log_id & ログ解析]

        Step3 --> CauseBranch{エラーの原因種別}

        CauseBranch -- A. テストスクリプトの不具合<br/>(待機不備/アサーションミス/環境構成) --> Step3A[3-A. テストコード自律自動修復<br/>(ユーザー承認 不要)]
        Step3A --> RetryCheck{リトライ回数 <= 5回？}
        RetryCheck -- はい --> Step2A
        RetryCheck -- いいえ (5回超過) --> Step3A_Fail[スクリプト修復不能通知<br/>ユーザーへエラー報告]

        CauseBranch -- B. システムの不具合<br/>(バックエンド/フロントエンド/DBバグ) --> Step4[4. エラー原因・解決案提示<br/>根本原因 & コードDiff提示]
        Step4 --> Step5[5. ユーザー承認 & システム修正<br/>(人間承認獲得後にコード修正)]
        Step5 --> Step2A
    end

    StepReport --> End([シナリオテストフェーズ完了])
```

### 各ステップの作業詳細

| ステップ | 名称 | 概要・詳細 | 主担当 |
| :--- | :--- | :--- | :--- |
| **(1)** | **シナリオ作成・自動化** | 画面仕様書、バックエンドAPI仕様書、およびビジネスロジック仕様書に基づき、機能検証・データ連携・画面アサーションを行うテストコードを構築する。 | AI (Antigravity) |
| **(2-A)** | **DB全ドロップ & 復元 (前処理)** | 自動テスト実行前に、テスト用DB (`data/app.db`) を初期化・クリーンなデータ状態へ完全復元する。これにより反復実行時のデータ不均衡・汚染をゼロにする。 | 自動化基盤 / AI |
| **(2-B)** | **自動テスト実行・レポート** | ヘッドレス実行およびAPI連携テストを全自動で実行し、Pass/Fail結果、ログエビデンスを集約したレポートを出力する。 | AI / 自動化基盤 |
| **(3)** | **原因分類・追跡 (Cause Tracking)** | 不合格ケース発生時、`log_id` またはエラーログをキーに解析を行い、エラー原因が「テストスクリプトの不具合」か「システムの不具合」かを判定する。 | AI (自律デバッグ) |
| **(3-A)** | **テストスクリプト自律自動修復 & リトライ** | エラー原因が**テストスクリプトの不具合**の場合、AIが自律的にテストコードを修復し、**ステップ2-A（DB復元）を経て最大5回まで自動リトライ**を行う。 | AI (Antigravity) |
| **(4)** | **エラー原因・解決案提示** | エラー原因が**システムの不具合**の場合、発生原因、影響範囲、およびコード修正案（Diff）を整理し、ユーザー（人間）に提示する。 | AI (Antigravity) |
| **(5)** | **ユーザー承認 & システム修正** | ユーザーが提示された修正案を確認・承認した後、実際のシステムソースコード修正を行い、`docker compose up -d --build` でコンテナを再構築する。 | ユーザー(承認) / AI(修正) |
| **(6)** | **再テスト・回帰テスト** | システム修正後、ステップ2-A（DB復元）を経てテストシナリオを再実行し、不具合解消の確認および他機能への影響が無いことを検証する。 | AI / 自動化基盤 |

## 3. 自動テスト環境・構成要件

### 3.1 テスト専用データベース Restore（全テーブル自動復元）方針
- 各テスト実行開始前に DB (`data/app.db`) をシードデータ / 初期スキーマ付きクリーン状態に自動修復・復元します。

### 3.2 Cloud Run IAP 認証モック環境
- テスト実行時、認証用ヘッダー (`x-goog-authenticated-user-email: testuser@example.com`) を適用したリクエスト検証を実施。

### 3.3 GCS 画像連携モック環境
- 画像アップロード・参照処理はローカルのダミー画像参照およびモックストレージにマッピングし、画像圧縮・保存処理の整合性を検証。

### 3.4 構造化ロギングおよびデバッグ連携
- テスト実行中にエラーが返却された場合、`log_id` (UUIDv4) をキーにバックエンド標準出力ログを検索・抽出して原因究明を実施。

## 4. 網羅的テストシナリオ案

### **シナリオ01: 認証・ヘルスチェック・セッション管理**
- バックエンド `/health` エンドポイントが正常に 200 OK を返却すること。
- IAP 認証ヘッダー受け渡しおよびユーザー識別ロジックの正常動作検証。

### **シナリオ02: ダッシュボード表示・サマリー集計**
- ダッシュボードの主要サマリー（総走行距離、総上昇量、総ライド回数、累積滞在スポット数）の集計ロジック検証。
- 訪問回数上位ランキング（TOP 10）および直近アクティビティ表示の正確性検証。

### **シナリオ03: アクティビティ・滞在スポット一覧 & CRUD操作**
- アクティビティ一覧の検索・リアルタイムキーワード絞り込み・ソート・ページネーション検証。
- 滞在スポット一覧および詳細・編集・削除モーダル連携の動作確認。

### **シナリオ04: マスタ管理機能 (CRUD)**
- 自転車マスタ (`bikes`) の登録・編集・削除・バリデーション。
- 滞在カテゴリマスタ (`place_categories`) の登録・編集・アイコン判定設定。
- 定番ルートマスタ (`routes`) および タグマスタ の参照・更新。

### **シナリオ05: 可視化・グラフ集計機能**
- Stravaアクティビティに基づく Bike ID 別のメトリクス集計（走行距離、上昇量、時間、回数、カロリー）。
- タイムレンジ切り替え（年間・月間・週間）による再集計ロジックの正確性。

### **シナリオ06: クラウドストレージ (GCS) 画像連携 & Canvas 圧縮**
- 滞在記録への写真添付・コメント保存処理。
- WebP 80% 圧縮変換および GCS 保存 URL/外部Web参照 URL の保持動作検証。

### **シナリオ07: ヒートマップ表示 & 定番ルート優先統合**
- Strava アクティビティ Polyline のヒートマップ描画用データ構造確認。
- 類似度 70% 超の定番ルートに紐づくアクティビティの代表 Polyline 統合表現検証。

### **シナリオ08: 異常系・境界値・AIロギング機能**
- 不正なリクエストパラメータに対する HTTP 400 / 422 レスポンスおよび `log_id` 付与の検証。
- 動的ログレベル変更 API (`POST /api/internal/logger/level`) による DEBUG モード切替の検証。
