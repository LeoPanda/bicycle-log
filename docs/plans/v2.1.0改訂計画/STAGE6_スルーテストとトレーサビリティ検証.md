# STAGE 6 詳細作業手順書: スルーテストとトレーサビリティ検証

- **ステージ番号**: STAGE 6
- **主担当エージェント**: 🛡️ 品質監査スペシャリスト (`qa-engineer`)
- **統括**: 👑 プロジェクトコンダクター (`conductor`)
- **目的**: 改訂後の全機能が正常に連携動作することをエンドツーエンドで検証し、モック有効/無効両モードでのスルーテストを自動完遂するとともに、要件トレーサビリティ機械検証（`traceability_checker.py --mode full`）を PASS させる。
- **所要想定時間**: 1 セッション
- **スレッドクローズ基準**: スルーテスト 100% 成功およびトレーサビリティ検証 PASS 後、ユーザー承認を得て Git コミットを実施。

## 1. シナリオテスト計画書の策定

担当: 🛡️ `qa-engineer`

`docs/plans/scenario-test/v2.1.0_シナリオテスト計画書.md` を作成する。

### 必須検証シナリオ群（異常系比率 20% 以上）
1. **自転車・ギア管理シナリオ**:
   - [正常系] 新規自転車登録 ➔ デフォルトバイク変更 ➔ 走行ログ反映
   - [異常系] 重複名・不正な初期積算距離のバリデーションエラー
2. **Strava 連携・アクティビティ同期シナリオ**:
   - [正常系] Strava 同期トリガー ➔ アクティビティ取り込み ➔ GPSストリーム解析 ➔ 走行ログ生成
   - [異常系] レートリミットエラー（HTTP 429）時のリトライ・二重キャッシュフォールバック
3. **滞在スポット検知・手動編集シナリオ**:
   - [正常系] 停止区間の自動クラスタリング ➔ スポット名自動付与 ➔ 写真アップロード（WebP変換）
   - [異常系] 破損画像・巨大ファイルアップロード時の HTTP 400 ガード
4. **定番ルート登録・マッチングシナリオ**:
   - [正常系] 走行ログから定番ルート作成 ➔ 新規アクティビティとのポリラインマッチング
   - [異常系] ポリライン欠落データのハンドリング
5. **統計分析・ダッシュボード集計シナリオ**:
   - [正常系] 月間・年間の距離・滞在カテゴリ集計 ➔ ヒートマップ描画データ整合性
6. **モック透過切替検証**:
   - `VITE_ENABLE_MOCK=true`（MSW モード）での全画面描画疎通
   - `VITE_ENABLE_MOCK=false`（実バックエンド接続モード）での完全一致検証

## 2. 自動テストの反復実行と自律修復ループ（最大5回）

テスト実行中に不具合が検出された場合、以下の自律修復ループを実行する。

```bash
# 1. バックエンド結合テストの実行
pytest backend/tests/ -v --cov=backend/app

# 2. フロントエンドモック・型チェック
cd frontend && npm run build && cd ..
```

- **自律修復の適用ルール**:
  - ドキュメント、テストスクリプト、設定ファイルは `qa-engineer` が直接修復可能。
  - システム本体コードの修正が必要な場合は、`qa-engineer` が Unified Diff 案を作成し、コンダクターの統括下で `backend-engineer` または `ui-designer` が適用する。
  - エラー根本原因（RCA）が発生した場合は、即座に `wiki/patterns/local/RCA-*.md` へ記録する。
